# Разбор кейса и технические решения

## Что в действительности покупают 100 баллов

Исходный кейс: 30 — Kubernetes/Gateway, 25 — воспроизводимость, 20 — мониторинг/логирование, 15 — техническое качество/безопасность, 10 — документация/дополнения. Это не пять независимых рекламных блоков: дополнительные возможности не компенсируют неработающую основу. Условие прямо говорит, что собственное приложение не является целью и не даёт дополнительных баллов.

**Приоритет разработки:** проверяемая основа → воспроизведение на чужой машине → связь запроса и телеметрии → контролируемая ошибка → документация и честные ограничения. Победу, 100 баллов и отсутствие равных предсказать невозможно: неизвестны другие работы и оценка жюри. SIGNAL оптимизирован под структуру критериев, а не под количество установленных инструментов.

## Отличие: отчёт является частью продукта

Типичная слабая защита показывает зелёные Pod и заранее открытый dashboard. Здесь контрольный запрос получает уникальный proof_id; проверяются ответ через Gateway, реальные targets/метрики, затем этот идентификатор находится через API Loki. Отрицательные контроли — чужой hostname, запрещённый прямой доступ к Service, HTTP 503 при живом health endpoint и недостаточное число samples — проверяют сами механизмы контроля.

Это сочетание инженерных практик для данного кейса, **не заявление о научной новизне или невозможности повторить решение**. Report HTML автономен; эксперт может проверить исходный JSON, повторить команды и сопоставить commit/version.

## ADR-01: kubeadm вместо сокращения пути через k3s

Кейс отдаёт приоритет kubeadm. Основная установка использует стандартные компоненты, один выделенный узел, containerd и воспроизводимый bootstrap. kind остаётся инструментом CI: одинаковые прикладные конфиги и Cilium, но отдельный, честно указанный patch Kubernetes. Разработка многонодового kubeadm-кластера до выполнения обязательной части увеличила бы инфраструктурные требования и поверхность отказов.

## ADR-02: Cilium с сохранённым kube-proxy

Нужна не декларативная NetworkPolicy на бумаге, а исполняемая изоляция, проверяемая отрицательным запросом. Используем Cilium как CNI; не добавляем одновременно kube-proxy replacement, BGP, Hubble и service mesh. Это ограничивает число новых сетевых режимов при достаточном контроле доступов. Совместимость выбранной ветки проверена по официальной таблице; E2E на целевой машине обязателен.

## ADR-03: Envoy Gateway + NodePort, не Ingress и не фиктивный LoadBalancer

Gateway API — обязательный интерфейс. Envoy Gateway реализует HTTPRoute/hostname/path/header/TLS/weights. NodePort даёт доступ без покупки LB, настройки MetalLB IP-пула или предположений о доступности L2 в виртуальной/облачной сети. В случае реального внедрения его заменит корректный инфраструктурный LoadBalancer; это смена внешнего транспорта, не отказ от API.

EnvoyProxy фиксирует имя Service и NodePorts. Версию Envoy data plane намеренно не задаём независимо от версии контроллера: upstream предупреждает о риске несовместимых xDS-конфигураций. HTTP-проверка остаётся обязательной даже при зелёном readiness.

## ADR-04: Fluentd, а не похожий по имени агент

В кейсе разрешены Fluentd или Filebeat. **Fluent Bit, Promtail или Alloy не подставляются вместо обязательного компонента.** Выбран Fluentd из опубликованного образа Grafana с Loki plugin; сбор CRI stdout/stderr через DaemonSet, filesystem buffer и один worker. Вызов /missing генерирует реальную ошибку Nginx, а не синтетический текст, записанный непосредственно в Loki.

Loki обеспечивает централизованный поиск без тяжёлого полнотекстового индекса. request_id/proof_id не являются stream labels. Не делаем обещаний exactly-once и честно ограничиваем поддержку длинных/multiline записей.

## ADR-05: небольшой детерминированный renderer вместо собственного Helm-чарта

Kubernetes принимает JSON; Python стандартной библиотеки позволяет выразить одинаковые security defaults, checksum конфигов, selectors и версии без дополнительных зависимостей Jinja/PyYAML. Сгенерированные manifests доступны для review. Helm оставлен там, где он действительно полезен: официальные chart сетевых компонентов. Это не генерация ресурсов «вслепую»: static tests проверяют связи, а deploy делает server-side dry-run с настоящими CRD.

Недостаток: render.py — собственный код, который нужно тестировать. Он включён полностью; generated snapshots проверяются на точное совпадение и не являются независимым вторым источником истины.

## ADR-06: canary gate как воспроизводимый эксперимент

30 запросов к canary cohort на каждом шаге не дают плохому backend раствориться в 90% здорового трафика. Проверяются не только status, но и тело/версия, p95, samples и доступность наблюдаемости. Намеренный HTTP 503 при живом /healthz показывает, почему Kubernetes readiness не равен корректному пользовательскому ответу.

Веса переключает CLI, а не долговременный controller. Полученные до завершения `SIGINT` / `SIGTERM` переводят прерванную операцию в попытку восстановления baseline; после неё проверяются фактические веса/ответ приложения или прежнее число реплик Loki. Прерванный сценарий остаётся неуспешным даже при успешном cleanup. Canary согласует поздние сигналы до финальной записи отчёта, сохраняя открытые forward для проверки; после явной границы завершения сигнал при закрытии forward не отменяет уже успешное продвижение 100%. При недоступном API, `SIGKILL` или потере VM автоматическое восстановление не гарантируется; recovery marker оставляется для ручного решения по runbook.

Промышленное развитие — Argo Rollouts/Flagger с окнами наблюдения, baseline comparison и эксплуатационным владельцем SLO. Обработчик сигналов и короткий CLI-эксперимент не заменяют постоянно работающий controller.

## ADR-07: local PV и прозрачная граница надёжности

PVC переживают Pod restart; Retain сохраняет данные при ошибочном удалении claim. Это существенно сильнее пустых ephemeral volumes для истории метрик/логов, но не backup. Для одного узла не маскируем host storage под распределённую систему. Пределы retention/буфера и low-disk alert уменьшают риск переполнения, не заменяя реальные quotas и мониторинг диска.

## ADR-08: общий kernel lock вместо несогласованных операций

Deploy, canary/demo, log-delivery и acceptance должны видеть один `.state/workflow.lock`. Используем Linux `flock`: конкурирующий процесс отказывается от запуска, вложенный acceptance → deploy наследует реальный дескриптор той же рабочей копии. Это позволяет держать lock до завершения восстановления и записи отчёта без self-deadlock во вложенной команде. Переменная окружения служит только подсказкой; файл, его identity и владение kernel lock проверяются.

Цена решения — локальная область координации: другая рабочая копия, прямой `kubectl` и внешние контроллеры обходят этот протокол. Не добавляем Kubernetes Lease или внешний coordinator до необходимости нескольких операторов/хостов. Наличие lock-файла не считается признаком живого владельца; удаление файла не является штатным способом остановить операцию.

Recovery marker создаётся перед опасным изменением: canary marker задаёт здоровую конфигурацию и stable 100%, Loki marker сохраняет UID Deployment и исходное число реплик. Он остаётся при неудачном cleanup; оператор проверяет действительное состояние, для Loki — UID и guarded scale, и возвращает baseline только после прекращения конкурирующих действий. Marker удаляют после проверки по runbook. Это средство восстановления после прерывания, не обещание гарантированного rollback при любом отказе.

## Статус новых механизмов

Полные green прогоны `efa05ee` и `d24163f` подтверждают предыдущую версию. Новые common lock и signal recovery пока не объявляются прошедшими runtime-проверку. Unit/process-тесты проверяют kernel lock и обработчики; `make operation-check` на Linux с работающим Kubernetes проверяет отказ конкурирующей операции до изменений и восстановление canary после настоящих `SIGINT` / `SIGTERM` с доступным API. SIGINT направляется группе процессов оператора, SIGTERM — PID. Дочерний сценарий обязан сохранить FAIL и сигнал; safety report требует здоровый baseline, удаление marker и освобождение lock. Он не доказывает восстановление Loki после сигнала или canary при отказе API.

Финальная упаковка требует свежие успешные Ubuntu acceptance и operations report для одного чистого HEAD. Сохранение marker при неудачном cleanup проверяется отдельно; ручная инструкция не считается результатом runtime-проверки.

## Что добавить после подтверждения новой версии — телеком-контекст

1. Несколько площадок / edge: отдельные кластеры, site labels, локальная автономность, централизованный сбор по защищённому каналу. Нужны VM/сеть/PKI и модель разрывов связи; платежи облаку необязательны.
2. Реплицированное хранение: несколько worker-узлов, CSI, S3-совместимое хранилище Loki и off-node backup с проверкой восстановления. Нужны дополнительные диски/узлы и бюджет хранения.
3. Изоляция абонентских/клиентских потоков: tenant-aware authorization, quotas, mTLS, очистка PII и формальные правила хранения. Один Loki label сам по себе не даёт изоляцию арендаторов.
4. Настоящий SLO: определение хороших событий, стабильный поток измерений, multiwindow burn-rate alerts и сравнение canary с baseline. Короткий synthetic тест не заменяет месячный SLA.
5. Защита цепочки поставки: digest для всех transitive images, signature verification, SBOM/CVE scanning, полный offline bundle и подписанный release manifest. Нужны registry, ключевая инфраструктура и процесс обновлений.

Эти пункты — предложения, не заявленная функциональность текущего репозитория.
