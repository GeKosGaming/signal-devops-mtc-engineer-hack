# Сценарий защиты: «покажем не обещание, а эксперимент»

До защиты: настоящая Ubuntu acceptance зелёная, паспорту соответствуют факты, `.state` не опубликована, baseline `make deploy && make verify`, Grafana открыта через localhost. Не изображать живой demo заранее подготовленным отчётом без пояснения.

## 1. Архитектура и пользовательский результат

«У приложения намеренно минимальная логика — Nginx возвращает Hello World. Основной предмет решения — kubeadm, Gateway API и проверяемая эксплуатация. Никакой коммерческий сервис не нужен».

Показать hostname HTTP curl, X-Release и TLS с `--cacert`. Затем `HTTPRoute` и соответствующий current-generation статус. Подчеркнуть: запрос идёт через Envoy, а не обходной port-forward прямо к backend.

## 2. Один запрос — три наблюдения

Запустить `make verify`, открыть report.html: уникальный proof_id в ответе, непустые реальные Prometheus targets/counter, найденный JSON access-log через Loki. Отдельно показать реальную missing-file ошибку и её собранный stderr. Здесь нельзя подменить Fluentd агентом, не разрешённым условием.

## 3. Проверим сам контроль

Запустить `make demo`. Показать измеренное распределение 90/10; затем faulty canary отвечает 503, но /healthz остаётся 200. Gate отклоняет canary по реальному ответу, возвращает stable 100%, подтверждает ответ и восстанавливает canary-конфиг.

После удаления одного stable Pod показать фактические число ошибок и длительность восстановления. Не говорить «ноль ошибок», если отчёт содержит иное; это лабораторный результат одного прогона, не SLA и не отказоустойчивость единственного узла.

## 4. Буфер при отказе Loki

Запустить `make log-delivery` только на выделенном стенде. Скрипт временно останавливает Loki, посылает 20 запросов с уникальными ID и восстанавливает прежнее число реплик. В отчёте показать реально найденные ID, задержки, пропуски и наблюдаемые дубли. Нулевые пропуски в коротком опыте не доказывают exactly-once или доставку при любом отказе. При прерывании и неудачном restore читать `.state/log-delivery-restore.json` и восстановить Deployment по сохранённому числу реплик, проверив UID.

## 5. Повторяемость и честная граница

Показать acceptance: две установки, сохранены Pod/PVC UID и публичные TLS-сертификаты, проверки до и после. Завершить ограничениями: один узел/local storage, короткие логи, synthetic gate, нет заявленного exactly-once или production HA. Развитие для телеком — несколько edge-площадок, локальный буфер при разрыве WAN, tenant isolation и replication.

## Что отвечать на вопросы

**Почему не своё приложение?** В условии прямо сказано, что это не цель и не источник дополнительных баллов.

**Почему не полный GitOps/mesh/ELK?** Они увеличивают зависимости до подтверждения обязательного пути. Вложение сделано в повторяемость и отрицательные проверки; дополнительные компоненты должны иметь измеримую пользу.

**Почему Prometheus не доказывает точное число пользовательских запросов?** stub_status включает probes/scrapes. Поэтому есть отдельное доказательство конкретного запроса в Loki, а counter проверяется как реальная собираемая метрика, без ложной причинной интерпретации.

**Это уникальная технология?** Нет, это тщательно собранное применение известных практик с необычно удобным и строгим протоколом проверки для данного кейса.
